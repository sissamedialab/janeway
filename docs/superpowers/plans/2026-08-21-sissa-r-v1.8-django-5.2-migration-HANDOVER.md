# Django 5.2 / Python 3.13 Migration — Handover Notes

This branch (`migration/1.8-phase7-pep440-compat-release`, stacked on 7 prior phase
branches, ultimately based on `sissa/r-v1.8.x`) completes an 8-task migration of this
codebase from Django 4.2.30 to Django 5.2.17, and from a Python floor of `>=3.9` to a
verified `3.10`–`3.13` range. Full plan, phase-by-phase execution detail, and every
task's review are recorded in the session that ran this migration; this file exists so
the two decisions below don't get lost between here and whoever merges this branch.

## Two things that need an owner decision before deploy — not bugs, not fixed here

### 1. `cms.SubmissionItem` needs a new migration, deliberately not generated

`django-modeltranslation` 0.20.3 (bumped in this migration) wants to generate a new
migration adding 7 new per-language UNIQUE constraints to `cms.SubmissionItem`
(`journal` × `title_cy/de/en/en_us/es/fr/nl`). **This was deliberately not generated
anywhere in this migration** — it tightens uniqueness against data that may already
exist in production (two submission items sharing an empty-string or otherwise-equal
translated title within the same journal would raise an `IntegrityError`), and it's a
genuine behavioural tightening (editors currently *can* give two items the same
non-English title; after this migration lands they could not).

**Before this is ever generated**: query production for duplicate non-NULL
`title_<lang>` values per journal, and get a product decision on whether per-language
title uniqueness is actually wanted.

**Consequence in the meantime**: `manage.py makemigrations --check --dry-run` will
report this as pending indefinitely until it's resolved. If any CI pipeline gates on
that check (SISSA's `.gitlab-ci.yml` includes a template from `wjs/wjs-profile-project`
not reviewable from this branch — check whether it runs this check), that job will be
red until the decision above is made.

### 2. `USE_L10N`'s removal silently turns localization on — changes 149 template date renders

The old `USE_L10N = False` setting was deprecated-but-still-effective under Django 4.2.
Django 5.2 removes the setting from `django.conf.global_settings` entirely, which
**turns localization on**. Consequence: `DATETIME_FORMAT` in `janeway_global_settings.py`
(the project-level explicit format) is now ignored in favor of the active locale's own
format — e.g. a date that rendered as `2026-08-21 15:04` now renders as
`Aug. 21, 2026, 3:04 p.m.`. Non-English `LANGUAGES` (`fr`/`de`/`es`/`nl`) also now
localize decimal separators. No test in the suite asserts on rendered date strings, so
this passed every test run in the migration without being caught until the final review.

**Decision needed**: accept Django's new locale-driven formatting (likely fine, arguably
more correct for a multi-language platform), or restore the old fixed formats via a
`FORMAT_MODULE_PATH` module. Recommend looking at one rendered article page and one
issue page before deploy to see the actual visual difference.

(Note: `DATE_FORMAT`, as opposed to `DATETIME_FORMAT`, is unaffected by this migration
either way — it's been unreachable since before this migration due to a pre-existing
typo, `DATE_FORMT`, in `janeway_global_settings.py`.)

## Needs a visual QA pass, not a decision

Django 5.0 changed the default form-renderer template from table-based to
div-based markup. Six admin-only templates that render `{{ form }}` bare pick up this
new markup: `admin/elements/confirm_delete.html`, `admin/elements/confirm_remove.html`,
`admin/core/request_submission_access.html`,
`admin/core/affiliation_update_from_orcid.html`, `admin/elements/issue/new_galley.html`,
`admin/cms/media_files.html`. All six are staff-only (none are in `src/themes/`, so no
public-facing page is affected), and the old markup was arguably broken HTML (bare
`<tr>`s with no enclosing `<table>`) — but nothing in the test suite verifies rendered
markup, so this should get a quick visual check before deploy, not be assumed fine.

## Known, pre-existing, deliberately preserved — not introduced by this migration

- **91 pre-existing test failures/errors** (34 failures + 57 errors, out of 893 tests)
  existed on `sissa/r-v1.8.x` before this migration touched anything, confirmed stable
  across a fresh venv rebuild. Concentrated in `security` (40) and `submission` (24),
  with the rest spread across 9 other apps. This migration's acceptance bar throughout
  was "the same known failures, no new ones" — not a green suite. The exact list is
  in this session's `.superpowers/` workspace (`baseline-known-failures.txt`); worth its
  own separate investigation, unrelated to this migration.
- `pdfkit` (CVE-2025-26240, unpatched) is pinned exactly as before and was never
  verified under Python 3.13 — a deliberate scope decision, not an oversight. The code
  paths using it are candidates for removal in a future change.
- `django-hCaptcha` is pinned exactly as before, verified to still work correctly under
  Django 5.2 / Python 3.13 via ad hoc checks (not persisted test coverage), flagged as
  obsolete (no release since 2022), with the replacement decision (a verified working
  fork, `django-recaptcha`, or something else) explicitly deferred.
- `packaging` and `pytz` (`~=26.3` / `~=2024.1.0` after this migration) both use a
  version-numbering scheme where the compatible-release operator locks more tightly
  than might be expected — `pytz` in particular is effectively frozen at its 2024.1
  release under this pin, worth a follow-up look given it's live runtime code
  (`core/middleware.py`, `core/models.py`).
- `ua-parser`'s explicit `requirements.txt` pin was removed as "unused" during this
  migration — the removal itself is correct (nothing imports it directly), but the
  reasoning was imprecise: it's a required transitive dependency of `user-agents`
  (which Janeway does use directly), not genuinely unused. It's now unpinned and free
  to resolve to whatever `user-agents` accepts, including a possible future major
  version with a different API.
